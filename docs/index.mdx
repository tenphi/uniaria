## Why UniAria

- **One implementation for every framework.** A component is one definition:
  its parts, props, events and behavior. Generic adapters bind it to
  [React](./api/react.md), to [Vue](./api/vue.md) and to
  [light-DOM custom elements](./api/elements.md), which work in any framework
  or none.
- **No re-renders for internal state.** Hover, press, focus, a highlighted
  option, an opening popover: UniAria writes these straight to the DOM. A React
  or Vue component renders again only for the state it
  [selects](./guide/state.md#reading-state).
- **Accessibility you can check.** Every component follows its
  [WAI-ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/patterns/)
  pattern. The same conformance scenarios run in Chromium, Firefox and WebKit,
  through every adapter, with a virtual screen reader on every push, and with
  VoiceOver and NVDA every night. [How it's tested](./guide/accessibility.md).
- **Native elements first.** A real `<button>`, `<input>` or `<dialog>` sits
  under each component, and overlays open in the browser's top layer: no
  portals, no moved nodes.
- **Headless, with hooks for your CSS.** A component's root carries
  `data-uni="<name>"` and its other parts `data-element`, all with state
  attributes such as `data-pressed` and `data-focus-visible`. Style them with
  any CSS you like, or with Tasty. [Styling](./guide/styling.md). Or start
  from the optional [default styles](./guide/default-styles.md), written
  against the same attributes.

## What it looks like

The same Switch, from React, from Vue and as a custom element:

```tsx
import { toggleSwitch } from '@uniaria/core/switch';
import { useComponent } from '@uniaria/react';

function WifiSwitch() {
  const wifi = useComponent(toggleSwitch, {
    defaultSelected: true,
    labelElementType: 'span',
  });
  return (
    <label {...wifi.parts.root}>
      <input {...wifi.parts.input} name="wifi" />
      <span {...wifi.parts.indicator}>
        <span data-element="Thumb" />
      </span>
      <span {...wifi.parts.label}>Wi-Fi</span>
    </label>
  );
}
```

```vue
<script setup lang="ts">
import { toggleSwitch } from '@uniaria/core/switch';
import { useComponent } from '@uniaria/vue';

const wifi = useComponent(toggleSwitch, {
  defaultSelected: true,
  labelElementType: 'span',
});
</script>

<template>
  <label v-bind="wifi.parts.root">
    <input v-bind="wifi.parts.input" name="wifi" />
    <span v-bind="wifi.parts.indicator">
      <span data-element="Thumb" />
    </span>
    <span v-bind="wifi.parts.label">Wi-Fi</span>
  </label>
</template>
```

```html
<script type="module">
  import '@uniaria/elements/switch';
</script>

<uni-switch>
  <label data-uni="switch">
    <input data-element="Input" type="checkbox" name="wifi" checked />
    <span data-element="Indicator"><span data-element="Thumb"></span></span>
    <span data-element="Label">Wi-Fi</span>
  </label>
</uni-switch>
```

You write the markup and the CSS. UniAria writes `role="switch"`, the label
and description links, `data-selected`, `data-focus-visible` and the other
state attributes, and keeps them up to date. The custom element reads its
starting state from your markup: the input's `checked` attribute here.
